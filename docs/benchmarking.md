# Бенчмарки и производительность `c-parser`

Этот документ описывает, как измерить производительность парсера и проверить
целевые показатели из ТЗ §6.4, а также фиксирует достигнутые результаты и
принятые оптимизации.

> Целевые метрики (ТЗ §6.4):
> - Парсинг + JSON-сериализация файла ~1 МБ — **не более 100 мс**.
> - Память на этапе анализа — **не более 10×** размера исходника.

---

## 1. Что измеряется и как

Бенчмарк построен на [`criterion`](https://docs.rs/criterion) и находится в
`crates/c-parser/benches/parser_bench.rs`. Он измеряет три фазы:

| Группа | Что измеряется |
|---|---|
| `parse/…` | лексический + синтаксический анализ (построение арены) |
| `serialize/…` | JSON-сериализация с lazy materialization |
| `end_to_end/…` | полный конвейер `parse` + `ast_to_json` (собственно целевая метрика 100 мс) |

Фикстура ~1 МБ генерируется детерминированно внутри бенчмарка функцией
`make_large_source` (смесь `typedef`/`struct`/`enum` и функций с арифметикой и
`if`/`return`), поэтому бенчмарк самодостаточен и не зависит от копии
`sqlite3.c` в репозитории.

## 2. Запуск бенчмарка

```bash
# из корня workspace (TMPDIR нужен из-за ограничений песочницы dev-окружения;
# в обычном Linux-окружении — просто `cargo bench -p c-parser`)
TMPDIR=/tmp cargo bench -p c-parser --bench parser_bench
```

Полный отчёт Criterion (с графиками) появляется в `target/criterion/report/index.html`.

## 3. Профиль памяти (dhat)

Профиль кучи снимается отдельным примером `dhat_profile` (использует `dhat` —
подсчёт каждого выделения + пиковое значение):

```bash
# профиль сгенерированной фикстуры ~1 МБ
TMPDIR=/tmp cargo run -p c-parser --example dhat_profile --profile release -- 1048576

# профиль реального C-файла (например, sqlite3.c):
TMPDIR=/tmp cargo run -p c-parser --example dhat_profile --profile release -- 0 /path/to/sqlite3.c
```

Программа выводит:

- `type_sizes` — размеры `Node` / `NodeData` / `TextSlice` (доказывают, что узел
  не хранит `String` — только `Span`);
- `source_bytes` / `ast_nodes` / `ast_errors`;
- `peak_alloc_bytes` — пиковое потребление кучи на этапе анализа (величина,
  которая должна быть ≤ 10×);
- `ratio (× source)` и `within 10x budget`.

После запуска создаётся `dhat-heap.json`, который можно открыть в HTML-вьюере
(`npx dhat-viewer` или `cargo install dhat-heap-view`), чтобы увидеть топ
мест выделения и подтвердить отсутствие `String::from_utf8` в горячем пути.

Альтернативно (как в ТЗ) — `valgrind --massif`:

```bash
valgrind --tool=massif --massif-out-file=massif.out \
  target/release/examples/dhat_profile 1048576
ms_print massif.out | less
```

## 4. Достигнутые результаты (тестовая машина, `--profile release`)

| Метрика | Цель | Измерено | Статус |
|---|---|---|---|
| `parse` 1 МБ | — | **~8.8 мс** (114 МБ/с) | — |
| `serialize` 1 МБ | — | **~39 мс** | — |
| **end-to-end (parse+serialize) 1 МБ** | **≤ 100 мс** | **~52 мс** | ✅ (запас ~2×) |
| Память на этапе анализа | **≤ 10×** | **~30×** | ⚠️ не достигнута |

### 4.1. Скорость — цель достигнута

Полный конвейер «лексер → парсер → JSON» укладывается в ~52 мс на 1 МБ, то
есть почти вдвое быстрее целевого порога 100 мс. Основное время (~39 мс)
занимает сериализация, что ожидаемо: она материализует каждый строковый
токен (`String::from_utf8_lossy`) и собирает JSON-строку — это O(N) по числу
узлов и по определению самодостаточного вывода.

### 4.2. Память — цель не достигнута (требуется доработка архитектуры)

Пиковое потребление на этапе анализа ~30× (а не 10×). Причина структурная, а не
«горячий путь»:

1. **Мелкозернистый AST.** Каждая лексема (`+`, `*`, `(`, литерал, идентификатор)
   порождает отдельный узел. В фикстуре ~1 МБ получается ~266 000 узлов
   (≈1 узел на 4 байта на плотном коде).
2. **Размер узла.** Даже после оптимизации `Node` занимает 88 байт:
   - `span: Span` — 8 байт (после перевода на `u32`, было 16);
   - `children: Vec<NodeId>` — 24 байта (плюс отдельный heap-буфер на каждый
     непустой список детей);
   - `data: Option<NodeData>` — 48 байт (внутри `TextSlice` = 16 байт).

   266 000 × 88 Б ≈ 23 МБ — только арена, плюс ~8 МБ на `children`-вектора.

#### Что уже сделано (и остаётся в коде)

- **`Span` переведён с `usize` на `u32`** (см. `docs/architecture.md` §7.2 —
  32-битные смещения покрывают файлы до ~4 ГБ). Это уменьшило `Node` со 104 до
  88 байт и `TextSlice` с 24 до 16 байт, снизив пиковую память вдвое (было ~61×,
  стало ~30×) и ускорив парсинг за счёт лучшей локальности.
- **Предварительное выделение арены** по длине исходника (`Arena::with_capacity`,
  эвристика `source_len / 12` в `arena_capacity_hint`) — убирает лавину
  реаллокаций `Vec<Node>` на больших входах.

#### Что необходимо, чтобы достичь 10× (перспектива, а не скоуп данного этапа)

- **Общая арена для `children`**: хранить детей узла не как
  `Vec<NodeId>` (отдельный аллокат на узел), а как диапазон
  `(offset, len)` в едином буфере индексов. Убирает ~24 байта + heap-буфер на узел.
- **Боксование `NodeData`**: для структурных узлов (без `data`) поле `data`
  сейчас занимает 48 байт впустую. Вынос `NodeData` в `Box`/индекс резко
  уменьшит `Node` для самого массового класса узлов.
- **Сжатие `TextSlice`**: представление `Span` двумя `u32` (или
  `NonZero`/дельта-кодирование) вместо enum с 16-байтовым `Box<str>`.

Эти изменения — изменение модели данных (архитектурное, этап 3 ТЗ), а не
оптимизация горячих путей, поэтому они вынесены за пределы текущего этапа и
зафиксированы здесь как известный лимит MVP.

### 4.3. Zero-copy подтверждён

Профиль dhat подтверждает отсутствие скрытых аллокаций строк на этапе анализа:
значения полей (`name`, `value`, `op`) хранятся в узле как `TextSlice::Span`
(ссылка на байтовый диапазон), а не как `String`. `materialize` вызывает
`String::from_utf8_lossy` **только** в момент сериализации (`serialize/mod.rs`),
что соответствует принципу lazy materialization (ТЗ §5.4). В профиле кучи этапа
парсинга нет `String::from`/`from_utf8` в горячем пути — только рост арены
`Vec<Node>` и `Vec<NodeId>` для детей.

## 5. Ручная проверка с готовыми бинарниками и тестовыми C-файлами

### 5.1. Собрать релизные бинарники

```bash
cargo build --release -p c-parser-cli
# бинарник: target/release/c-parser-cli
```

### 5.2. Подготовить тестовый файл ~1 МБ

```bash
# Склеить существующие фикстуры в один большой файл (или взять реальный):
cat tests/fixtures/*.c > /tmp/huge.c
# Довести до ~1 МБ, повторив содержимое:
for i in $(seq 1 200); do cat /tmp/huge.c; done > /tmp/one_mb.c
wc -c /tmp/one_mb.c   # должно быть ~1 000 000 байт
```

Либо использовать настоящий `sqlite3.c`:

```bash
wget -qO /tmp/sqlite3.c https://www.sqlite.org/2024/sqlite-amalgamation-3450100.zip  # пример
# или: скопировать первый 1 МБ любого крупного .c-файла
head -c 1048576 your_large_file.c > /tmp/one_mb.c
```

### 5.3. Замерить время end-to-end

```bash
/usr/bin/time -v target/release/c-parser-cli parse /tmp/one_mb.c -o /tmp/ast.json
```

- «Elapsed (wall clock) time» — время конвейера парсинг+сериализация
  (цель ≤ 100 мс на 1 МБ; на быстрой машине ожидается ~50–60 мс).
- «Maximum resident set size» (kbytes) — пиковое RSS процесса; разделив на
  1024 и на размер файла в МБ, можно грубо оценить кратность памяти.

Для точного замера только парсинга (без записи JSON в файл) используйте
бенчмарк:

```bash
TMPDIR=/tmp cargo bench -p c-parser --bench parser_bench -- end_to_end
```

### 5.4. Проверить корректность вывода

```bash
jq '.nodes | length' /tmp/ast.json            # число узлов
jq '.errors | length' /tmp/ast.json           # нефатальные ошибки (для чистого кода ~0)
jq -e '.version == "1.0" and .language == "c"' /tmp/ast.json
```

Валидация по схеме выполняется в тестах (`tests/schema_validation.rs`):

```bash
cargo test --test schema_validation
```

### 5.5. Проверить память на реальном файле (dhat)

```bash
TMPDIR=/tmp cargo run -p c-parser --example dhat_profile --profile release -- 0 /tmp/one_mb.c
# смотрим строки "ratio (× source)" и "within 10x budget"
```

## 6. Итог

- ✅ Бенчмарк на `criterion` запускается и выдаёт отчёт.
- ✅ Целевой показатель **100 мс** достигнут с запасом (~52 мс end-to-end на 1 МБ).
- ✅ Профиль памяти (`dhat` и, опционально, `valgrind --massif`) подтверждает
  zero-copy: в `Node` нет `String` — только `Span` (`TextSlice::Span`).
- ⚠️ Целевой показатель памяти **10×** не достигнут: текущее пиковое
  потребление ~30× ограничено моделью данных (мелкозернистый AST + 88-байтовый
  узел + отдельные `Vec<NodeId>` на детей). Оптимизация `Span→u32` и
  предвыделение арены включены в код; дальнейшее снижение требует изменения
  модели данных (общая арена детей / боксование `NodeData`), что относится к
  архитектурному этапу, а не к оптимизации горячих путей.
